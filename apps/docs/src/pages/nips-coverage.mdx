# NIP coverage

Velvet aims to give **every NIP a home** — a dedicated factory/parser, a feature in
the kernel stack, a generically-handled kind in the registry, or an explicit
parse-only round-trip. This isn't a marketing claim: a
[coverage meta-test](https://github.com/nostragent/velvet/blob/main/packages/nips/tests/coverage.test.ts)
enumerates the entire canonical [`nostr-protocol/nips`](https://github.com/nostr-protocol/nips)
index and asserts each one resolves to a real home. This page is that table, rendered.

## Legend

| Mark | Meaning |
| --- | --- |
| 🟢 **Module** | A dedicated typed factory + parser in [`@nostragent/nips`](/packages/nips) |
| 🔵 **Kernel** | First-class feature in [core](/packages/core) / [signers](/packages/signers) / [relay](/packages/relay) / [pool](/packages/pool) / [router](/packages/router) / [store](/packages/store) / [client](/packages/client) |
| ⚪ **Registry** | The kind is in the [kind registry](/packages/nips#the-kind-registry) — classifiable & renderable generically |
| ◽ **Parse-only** | Reserved-kind round-trip at v1 (typically a heavy external spec) |

Many NIPs carry more than one mark — e.g. NIP-40 has a builder *and* store-level
expiry; NIP-65 has a module *and* the router.

## Verifying coverage yourself

```bash
bun test packages/nips/tests/coverage.test.ts
```

The test fails if any canonical NIP lacks a home, if the home table lists a NIP
that no longer exists upstream, or if a NIP claimed as a module stops exporting
anything — so this page can't quietly drift from what the code actually ships.
