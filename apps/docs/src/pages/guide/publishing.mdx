# Publishing

`publish()` (and its sugar `note()`) returns a **thunk** — the event is signed and
added to your local store immediately, but the network I/O is deferred until you
`await` it. That gives you optimistic UX plus honest, per-relay results.

## A note

```ts twoslash
import { Nostr } from '@hopstr/client'
const nostr = await Nostr.create()
// ---cut---
const results = await nostr.note('gm')
//    ^?
```

Each entry is `{ relay, ok, reason }`. **Partial success is normal** — Velvet never
throws just because one relay rejected you.

```ts twoslash
import { Nostr } from '@hopstr/client'
const nostr = await Nostr.create()
// ---cut---
const results = await nostr.note('gm')
if (results.some((r) => r.ok)) console.log('it is on Nostr')
```

## Chained options & escape hatches

```ts twoslash
import { Nostr } from '@hopstr/client'
const nostr = await Nostr.create()
// ---cut---
await nostr.note('to a specific relay').to(['wss://my.relay']).timeout(8_000)
await nostr.note('must land somewhere').orThrow()      // throws only if EVERY relay rejects
```

## Optimistic undo

```ts twoslash
import { Nostr } from '@hopstr/client'
const nostr = await Nostr.create()
// ---cut---
const pub = nostr.note('oops, wrong window')
const event = await pub.event()            // already in the local store
pub.undo()                                 // rolls it back, before the network send
```

## Custom events

`publish()` takes any **event template** — a `{ kind, tags, content }` object. The
signer fills in `pubkey`, `created_at`, `id`, and `sig`, so you only describe the
event itself. That's all you need to publish a kind Velvet has never heard of.

### With the fluent builder

`build(kind, content?)` from `@hopstr/core` is the ergonomic way. Every method
chains, and the builder is itself a valid template, so you can hand it straight to
`publish()`.

```ts twoslash
import { Nostr } from '@hopstr/client'
import { build } from '@hopstr/core'
const nostr = await Nostr.create()
// ---cut---
await nostr.publish(
  build(30078, 'my app data')      // kind 30078: arbitrary app-specific data (NIP-78)
    .tag('d', 'settings')          // a 'd' tag makes it addressable/replaceable
    .tag('t', 'velvet')
)
```

Handy builder methods: `.tag(...values)` for a raw tag, `.addTags([...])` for
several, `.text(content)`, `.mention(pubkey)`, and `.at(created_at)` to pin the
timestamp (otherwise the signer stamps "now").

### From a raw object

If you'd rather not import anything, pass the template literally:

```ts twoslash
import { Nostr } from '@hopstr/client'
const nostr = await Nostr.create()
// ---cut---
await nostr.publish({
  kind: 30078,
  content: JSON.stringify({ theme: 'dark', relays: 3 }),
  tags: [
    ['d', 'settings'],   // identifier for an addressable (NIP-33) event
    ['t', 'velvet'],
  ],
})
```

JSON-in-content is a common convention — set `content` to your stringified payload
and reach for tags only for the fields you want relays to index and filter on.

### Reading it back

A custom kind is queried like any other event — by `kinds`, and for addressable
events by the `d` tag via `#d`:

```ts twoslash
import { Nostr } from '@hopstr/client'
const nostr = await Nostr.create()
const me = await nostr.pubkey()
// ---cut---
const settings = await nostr.queryOne({
  kinds: [30078],
  authors: [me],
  '#d': ['settings'],
})
```

## NIP helpers

For well-known kinds, `@hopstr/nips` ships typed builders so you don't hand-roll
the tags:

```ts twoslash
import { Nostr } from '@hopstr/client'
import { article } from '@hopstr/nips/nip23'
const nostr = await Nostr.create()
// ---cut---
await nostr.publish(article({ slug: 'hello', title: 'Hello', markdown: '# hi' }))  // kind 30023
```
