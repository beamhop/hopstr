# The `hopstr` CLI

`hopstr` is a Nostr daemon for your terminal, built on [`@hopstr/agent`](/packages/agent).
Run `hopstr listen` to stream your notifications (mentions, replies, DMs, reactions)
as they arrive, and use the one-shot commands to post, reply, DM, or react.

## Run it

The CLI is a Bun entrypoint — no build step:

```bash
bun run packages/cli/src/index.ts --help
# or, once linked on your PATH:
hopstr --help
```

## Identity

`hopstr` finds your key in priority order:

1. the `NOSTR_NSEC` environment variable
2. `~/.config/hopstr/config.json` → `{ "nsec": "nsec1...", "relays": ["wss://..."] }`

```bash
export NOSTR_NSEC=nsec1...
hopstr listen
```

Don't have a key yet? `id new` mints one — it's the only command that doesn't need
an existing identity:

```bash
hopstr id new --json
# → {"nsec":"nsec1...","npub":"npub1..."}
```

The `nsec` is the whole identity — keep it secret. The `npub` is your public handle,
safe to share.

Pass `--save` and `id new` writes the new nsec straight into the config file, so
you're set up in one step (existing relays are kept; an existing nsec is never
overwritten):

```bash
hopstr id new --save
# mints a key and saves it to ~/.config/hopstr/config.json
```

## Listen — your live notification stream

```bash
hopstr listen --json | jq .
```

On startup, `listen` **bootstraps your network presence** — it publishes your
profile (kind-0), relay list (kind-10002), DM relay list (kind-10050), and contact
list (kind-3) so other clients can discover and message you. Without the DM relay
list, apps like iris refuse to send you DMs (see the [DM guide](/guide/dms)). This
is idempotent: an existing profile or follow list is never overwritten.

Then it streams one event per line. With `--json`, each line is a JSON object:

| `type` | extra fields |
| --- | --- |
| `mention` / `reply` | `id`, `content` |
| `dm` | `text`, `dmKind` (`nip17` or `nip04`) |
| `reaction` | `emoji`, `targetId` |

Every event carries `from` (an npub) and `at` (unix seconds). Legacy NIP-04 DMs are
decrypted inline, so `text` is always plaintext. Drop `--json` for a human-readable,
labelled feed.

```bash
hopstr listen                      # pretty, labelled output
hopstr listen --since "2d ago"     # replay the last two days first
hopstr listen --relay wss://relay.example.com
```

## Post & interact

```bash
hopstr post "hello nostr"
hopstr reply <event-id> "totally agree"      # threaded (NIP-10)
hopstr dm npub1xyz… "hey!"                    # sent as NIP-17 gift wrap
hopstr react nevent1abc… 🤙                    # emoji defaults to +
```

## Manage your profile

Your profile is a kind-0 metadata event ([NIP-01](https://nips.nostr.com/1) +
[NIP-24](https://nips.nostr.com/24)): your name, bio, picture, and more. `profile get`
reads one — your own by default, or anyone's by npub/pubkey — and `profile set` updates
yours.

```bash
hopstr profile get                       # your own profile
hopstr profile get npub1xyz…             # someone else's
hopstr profile get --json | jq .         # → {"name":"Alice","about":"…"}  ({} if none)
```

Each `--<field> <value>` you pass on `set` is **merged onto your current profile**, so
updating one field never wipes the others:

```bash
hopstr profile set --name "Alice" --about "building on nostr"
hopstr profile set --picture https://alice.dev/me.png   # name & about preserved
hopstr profile set --bot true                           # coerced to a JSON boolean
hopstr profile set --pronouns they/them                 # arbitrary fields are allowed
```

Known fields (labelled in `get` output): `name`, `display_name`, `about`, `website`,
`nip05`, `lud16`, `lud06`, `picture`, `banner`, `bot`. Anything else is accepted and
stored as a string.

| Flag | Effect on `profile set` |
| --- | --- |
| `--<field> <value>` | set/overwrite that field, merging onto the current profile |
| `--<field> ""` | **clear** that field (the key is removed entirely) |
| `--replace` | overwrite the whole profile with exactly the fields you pass |

```bash
hopstr profile set --name "Alice" --about "starting fresh" --replace
```

## Read a thread

When a notification points at a reply or comment, you have one event id but no view of
the discussion around it. `thread` takes **any** node — the root, a mid-thread reply, or
a [NIP-22](https://nips.nostr.com/22) comment (kind 1111) — finds the thread root, and
reconstructs the whole conversation tree. The id may be raw hex, `note1…`, or `nevent1…`.

```bash
hopstr thread nevent1abc…
```

```
▸ alice: Anyone running Bun in prod?  (b0515780)
  └─ bob: yes, six months, zero issues  (f58d8032)  ← you asked about this
    └─ alice: what about memory under load?  (83524e2e)
```

It resolves [NIP-10](https://nips.nostr.com/10) reply markers and NIP-22 root/parent
tags, then expands replies breadth-first so the **entire** subtree is collected — even
replies that only reference their immediate parent. Each author shows their kind-0
profile name (falling back to a short npub), and the event you asked about is marked.

With `--json` you get the nested tree as `{ root, target, tree }`:

```bash
hopstr thread nevent1abc… --json | jq .tree
```

## Options

| Flag | Meaning |
| --- | --- |
| `--json` | one JSON object per line (machine-readable) |
| `--relay <url>` | add a relay (repeatable); **replaces** the defaults when given |
| `--since <when>` | for `listen`: unix timestamp, relative (`1h`, `2d ago`, `30m`), ISO date (`2025-06-01`), or natural (`yesterday`, `last week`) |
| `--help`, `-h` | show help |

## Pair it with an agent

`listen --json` is a clean event stream — pipe it into your own tooling, or skip the
CLI entirely and drive the same behaviour from code with
[`runAgent`](/guide/agent#autonomous-mode) for autonomous replies.
